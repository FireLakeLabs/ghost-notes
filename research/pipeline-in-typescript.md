# Audio-to-MIDI in TypeScript

> Provenance: written 2026-11-12 by a research agent working in the ODM repository, before Ghost Notes existed. "AGENTS.md", "docs/" and D-numbers refer to ODM. Line numbers refer to ODM's `tools/audio-to-midi/extract.py` at that date. Copied with song and band names removed (G4).

Research date: 2026-11-12. Read-only investigation; no repository changes. Read AGENTS.md, docs/decisions.md, extract.py, pyproject.toml and README.md. No inference benchmark was run and no audio quality was assessed.

Most orchestration and all MIDI logic can move to TypeScript. Basic Pitch already has an official TypeScript implementation. Beat This and Demucs have third-party ONNX exports, making a Python-free inference runtime plausible. A complete browser replacement is an engineering project, with ADTOF licensing and backend compatibility still unresolved.

## Actual pipeline and portability

References below are to tools/audio-to-midi/extract.py in the requested checkout.

| Step | Node | Browser | Existing implementation and caveats |
|---|---|---|---|
| Download | Straightforward orchestration using child_process and yt-dlp executable | YouTube URL ingestion is not a dependable browser-only feature: cross-origin access and changing extraction challenges require a service/local helper | Lines 90–128 invoke Python yt-dlp, read chapter metadata and cache source audio. A Node wrapper does not eliminate Python unless distributing yt-dlp's standalone executable. Keep upstream rather than reimplementing its extractors. |
| Decode/cut | Native ffmpeg/ffprobe subprocesses are the practical choice | Web Audio decoding and PCM slicing for supported uploads; ffmpeg.wasm for wider format support | Lines 131–166 probe chapters and decode at 44.1 kHz stereo. Chapter selection itself is plain data manipulation. Browser decoder support does not cover every FFmpeg format or embedded chapter metadata. |
| Six-stem separation | ONNX Runtime Node is plausible, with exported graph and host DSP | Technically plausible using ORT Web, but must prove operators, memory and throughput on supported devices | Lines 176–191 call demucs.api.Separator, then clip and write PCM16 stems. Preserve normalization, chunking, overlap, shifts, STFT/inverse STFT and sample rate; running a network alone is insufficient. |
| Beats/downbeats | ONNX Runtime plus matching feature extraction and postprocessor | Existing WebGPU-oriented exports make this credible | Lines 216–244 use final0, mono mix and dbn=False; infer meter by downbeat votes. Port minimal postprocessing, not a DBN replacement. |
| Pitched notes | Official @spotify/basic-pitch or existing ONNX weights | Official TF.js implementation exists | Lines 255–283 already select ONNX in Python. TS must preserve onset .5, frame .3, minimum 90 ms, frequency bounds, melodia behavior, velocity scaling and mono cleanup. Demo defaults differ. |
| Drum notes | Custom ONNX export feasible; not a ready npm swap | Research prototype feasible; WebGPU recurrent-op support is a particular risk | Lines 301–333 use the pinned ADTOF PyTorch port, frontend and PeakPicker at 100 fps; five GM classes, threshold-relative velocities and fixed .1 s notes. No maintained matching JS package or published matching ONNX/TF.js weights was verified. |
| MIDI/cache/chapters | Easy TS | Easy TS with browser storage/download adapters | Lines 341–439 assemble MIDI; 447–521 orchestrate/cache/summary; 550–574 choose chapters and manifest. Node fs maps directly; browser needs IndexedDB/OPFS or explicit file export. |

## Packages, weights and maintenance evidence

Maintenance observations use GitHub repository metadata fetched on the research date. A last push is evidence of activity, not a support promise.

- [Spotify basic-pitch-ts](https://github.com/spotify/basic-pitch-ts): official npm `@spotify/basic-pitch`, Apache-2.0, TF.js model included. Last push reported 2023-05-23: usable but dormant, so budget compatibility work. [Model tree](https://github.com/spotify/basic-pitch-ts/tree/main/model) reports one weight shard of **742,392 bytes**, excluding JSON and runtime. Python's existing ONNX option avoids a new model conversion. TF.js browser WebGL/WASM paths and Node native TF backend are choices; WebGPU needs separate validation rather than assuming this older package supports it unchanged.
- [Beat This upstream](https://github.com/CPJKU/beat_this): Python/PyTorch, MIT code and published weights. No official TS package verified. [musetric ONNX export](https://huggingface.co/musetric/beat-this-onnx) explicitly targets onnxruntime-web WebGPU and documents final0 lineage, frontend and window shape. Its cited upstream checkpoint is **81,058,141 bytes**; that is not a measurement of its ONNX download. [Chris-Kode export](https://huggingface.co/Chris-Kode/beat-this-final0-onnx) is **84,973,959 bytes**, includes a frontend, and documents different resampling and unverified mirror lineage. Prefer the export with directly traced upstream weights. These are community artifacts, not an upstream JS support commitment.
- [Demucs upstream](https://github.com/facebookresearch/demucs): MIT, archived; last push reported 2024-04-24. [StemSplit demucs-onnx](https://github.com/StemSplit/demucs-onnx) is MIT, a small community project; its [CLI documentation](https://github.com/StemSplit/demucs-onnx/blob/main/docs/cli.md) links existing six-stem ONNX weights. [HRSadeghi implementation](https://github.com/HRSadeghi/demucs-onnx) advertises JavaScript and browser/WebGPU inference for six-stem models. Treat those as implementation claims requiring reproduction. Plan **roughly 80–200 MB** for a six-stem FP32 artifact (estimate; exact export bytes not verified), plus runtime and working buffers. TF.js conversion is less attractive than the existing ONNX work because hybrid spectral/complex operations already need special handling.
- [ADTOF PyTorch](https://github.com/xavriley/ADTOF-pytorch): last push reported 2025-11-11; GitHub detects **no licence**. Repo tree reports bundled `.pth` weights **3,617,805 bytes**. This is checkpoint size, not a verified ONNX size. Its README documents conversion from original Keras and frontend differences. Exporting CNN/recurrent inference to ONNX is plausible; reproduce mel features, bidirectional context and peak picking. Original Keras offers another TF.js conversion route, but neither conversion nor its accuracy was tested here.
- [@tonejs/midi](https://github.com/Tonejs/Midi): MIT, browser/Node parsing and writing, tempo and time-signature data. Last push reported 2023-07-19: mature but dormant. Use ticks explicitly and inspect serialization. Lower-level [midi-file](https://github.com/carter-thaxton/midi-file) is an alternative for exact conductor/event control.
- [yt-dlp](https://github.com/yt-dlp/yt-dlp): actively changing upstream (last push reported 2026-11-04); source Unlicense, distribution dependencies can have separate terms. npm wrappers delegate extraction rather than port it.
- [ffmpeg.wasm](https://github.com/ffmpegwasm/ffmpeg.wasm): wrapper MIT, recent activity reported 2026-09-29; FFmpeg core and linked codecs retain their own LGPL/GPL obligations. [Published performance comparison](https://ffmpegwasm.netlify.app/docs/performance/) shows substantial overhead versus native, not a song-specific timing promise. Native FFmpeg licensing also depends on build configuration.
- [ONNX Runtime WebGPU documentation](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html): WebGPU is an execution provider, not a guarantee every exported operator runs on GPU. Check the actual graph/provider combination, transfers and fallback. Node CPU execution and browser WASM are separate performance targets.

## Licensing decision

The [original ADTOF repository](https://github.com/MZehren/ADTOF) explicitly licenses its contents **CC BY-NC-SA 4.0**. The port says its weights derive from that release but declares no licence of its own. The local README correctly flags both issues. Publicly readable source is not sufficient permission to redistribute the port. Converting weights to ONNX/TF.js does not remove non-commercial or share-alike conditions. Obtain explicit code and weight permissions or replace/retrain the drum model before commercial product distribution; hosting inference on a server does not itself resolve the restriction. Do not infer that generated MIDI automatically inherits the model licence; that is a separate rights question. Source recordings also remain separate: D13 prohibits repository redistribution without permission.

## Pure logic: small and portable, but preserve semantics

- Relative RMS gating (194–206, 475–478): Float32Array reductions and log10; default -30 dB (531). It gates transcription after separation, so it saves transcription time, not separation time. Current levels are rounded before thresholding. Chunked RMS can reduce memory; retain stereo/sample-count weighting and epsilon.
- Mono cleanup (286–298): sort and loop, keep louder near-simultaneous notes within 30 ms, truncate overlaps. Match Python ties and rounding explicitly.
- Grid (341–401): linear interpolation seconds→ticks at 480 PPQ, extend beat grid to zero/end, majority-vote pickup phase, emit a tempo for each changed beat interval. This preserves timing; it is not quantization. Keep pickup time signatures and 120 BPM fallback.
- MIDI (404–439): type 1, conductor plus ordered stem tracks, drum channel 9 (wire numbering), GM programs, note-off before note-on at equal ticks, minimum one tick duration. @tonejs/midi is suitable if its writer preserves these details; midi-file gives lower-level control. Compare parsed events and reconstructed seconds, not binary equality.
- Chapters/names (66–74, 117–120, 140–146, 550–558): trivial TS; preserve original chapter numbering after filtering and chapter-local note times. Browser file metadata extraction is separate from chapter selection.
- Cache/manifests (447–574): plain JSON and filesystem logic. Existing cache invalidation is existence-based: changing thresholds/model with old notes can reuse stale results. A port should record a versioned settings/model hash rather than silently retaining that weakness.
- MIDI-to-Strudel is not implemented in extract.py. It is additional work: map ticks to musical spans, drums/programs to chosen Strudel instruments, and decide how variable tempo is represented without silently replacing it with median BPM. Respect D2/D4/D11 and the existing src/strudel seam (D14).

## Timing: estimates, not measurements

Assumptions: 120–180 s song, modern desktop/laptop, warm model cache, sequential processing, six stems with four or five pitched stems surviving the gate. Numbers below are deliberately broad engineering budgets. They exclude initial downloads and are **not sourced benchmarks**. Mobile, integrated GPUs, thermal limits and unsupported operators can be substantially worse.

| Stage | Native Node CPU estimate | Browser WebGPU estimate, if supported | Browser WASM estimate |
|---|---:|---:|---:|
| Decode/cut | 1–10 s | 2–20 s (decode is not GPU inference) | 5–60 s with FFmpeg WASM |
| Six-stem Demucs | 3–20 min | 1–10 min | 15–90+ min or memory failure |
| Beat This final0 | 5–45 s | 2–20 s | 15–120 s |
| ADTOF | 3–30 s | 3–30 s; CPU fallback may dominate | 10–90 s |
| Basic Pitch, each surviving pitched stem | 5–45 s | 3–30 s | 15–120 s |
| Logic/MIDI | under 1 s | under 1 s | under 1 s |

These are planning ranges based on model structure, serial stem count and browser overhead, not extrapolations from the saved run. ADTOF WebGPU may fail entirely without graph adaptation; no finite runtime estimate applies until that is resolved. GPU acceleration in Node usually means a native GPU provider (for example CUDA), not assuming browser WebGPU is exposed through onnxruntime-node.

Memory arithmetic, not benchmark: three minutes of stereo 44.1 kHz Float32 PCM is about 63.5 MB; six stems alone occupy about 381 MB. Mix, spectra, intermediate activations, GPU duplicates and graph initialization can push usage above 1 GB. Process chunks/stems and release tensors. Weight download is not peak RAM.

Observed saved evidence: the first test session's manifest records a 573 s source with four chapter lengths approximately 124, 166, 142 and 141 s, `htdemucs_6s`, CPU and -30 dB. First chapter's piano is -51.9 dB and omitted, while other is -27.5 dB and transcribed; second chapter includes all six tracks. First chapter has a two-beat pickup. No elapsed-time field was found in that manifest; files existing prove completion, not speed or transcription accuracy. These are useful parity fixtures, kept outside the repository under D13.

## Realistic splits

Effort estimates assume one experienced developer, include validation but exclude new model training and legal permission lead time.

1. **Python extraction; TS post-processing/import (recommended first).** About 3–7 working days for grid, MIDI/JSON import, mappings and parity checks; 1–2 weeks if a polished import UI is included. Keep extraction standalone and import notes.json + beats.json (richer than MIDI alone), or MIDI. No model payload in the app; import should take under a second after files are available (estimate). User runs the local tool, waits its existing unmeasured duration, then imports. Risks: tempo semantics and instrument mapping; ADTOF remains restricted for extraction/distribution. This creates a useful product seam without changing inference.
2. **Node desktop/local helper, increasingly Python-free.** About 3–6 weeks: TS orchestration/postprocessing, native FFmpeg and standalone yt-dlp, Basic Pitch JS/ONNX, Beat This ONNX, Demucs ONNX. Keep a small Python ADTOF worker initially or replace it after permissions. Exact all-model parity and a packaged Python-free runtime may take 6–10 weeks. User installs a helper and supplies URL/file, sees progress and cached reruns; app bundle stays small, helper downloads roughly 200–400 MB of models/runtimes (estimate; package-specific native libraries can increase this considerably). CPU planning wait roughly 4–25 minutes/song; a native GPU could improve it, but needs a benchmark. Risks: ONNX host DSP, binary packaging, native dependencies and ADTOF rights. This is the most credible route to TS ownership of nearly all code.
3. **Fully browser-local uploaded audio.** About 6–12+ weeks for a supported desktop WebGPU prototype and robust workers/chunking/progress; production mobile coverage is not established. Start with uploaded audio and manual/provided chapters. General YouTube URL ingestion would still need an external component, so it would no longer be fully browser-only. Lazy model/runtime payload roughly 200–400 MB (estimate); first load at 50 Mbit/s ideally 32–64 s plus initialization, subsequent loads cacheable. Supported desktop WebGPU planning wait about 2–15 minutes/song, WASM potentially tens of minutes to over an hour or failure. Primary risks: graph compatibility, recurrent operators, memory pressure, background tab/device behavior, numerical parity and drum-model licence. Offer stem upload/Basic Pitch-only mode as an earlier useful subset.

Recommendation: implement split 1 first, retaining a versioned neutral notes/beats/stems schema. Then validate split 2 with the existing four chapters: compare beat/downbeat positions, note events, pickup, channels and tempo reconstruction. Benchmark cold/warm loads and peak memory on named hardware before promising speed. Treat a browser pipeline as a later optional mode, gated by a successful six-stem WebGPU experiment and a cleared or replaced ADTOF model.
